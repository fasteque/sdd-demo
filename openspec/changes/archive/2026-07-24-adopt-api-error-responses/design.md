## Context

Every error response in this API today is either a bare `ResponseStatusException` with a reason string that Spring Boot's default error handling does not serialize into the body (confirmed empirically: `curl`ing the blank-tags 400 returns `{"timestamp","status","error","path"}` with no message), or a framework-default Bean/method-parameter validation error body whose shape has never been standardized. `docs/tech-stack.md` explicitly flagged this as deferred: "no custom error body shape yet (revisit if inconsistency becomes a problem)." The `sdd-demo-api-contracts` reference store defines `api-error-responses`, a platform-wide convention this repo has not yet adopted: every 4xx/5xx response must return `{ "error": { "code", "message", "traceId", "details"? } }`, with `details` required for validation failures and no duplicate status field.

This repo is OAS-first (`openapi/openapi.yaml` is the wire-contract source of truth) and already generates server models via `org.openapi.generator` (kotlin-spring, `interfaceOnly: true`) rather than hand-declaring DTOs for OAS-covered shapes (`docs/tech-stack.md`). No existing pattern in this repo handles cross-cutting error mapping — `AssetController` throws `ResponseStatusException` directly at each call site with no shared advice/handler.

## Goals / Non-Goals

**Goals:**
- Every 4xx/404 response currently produced by `asset-management` (missing required field, asset not found, invalid page, invalid size, blank tags) returns the platform's structured error envelope.
- The envelope's `Error`/`ErrorDetail` shapes are OAS-first like every other model in this repo — declared in `openapi/openapi.yaml`, generated via `openApiGenerate`, and constructed from the generated model classes in a single shared handler, not hand-declared DTOs.
- `error.code` values are stable per error condition, independent of message text (per the platform spec's second requirement).

**Non-Goals:**
- No new tracing/correlation-ID infrastructure (Micrometer Tracing, MDC-based request correlation, log pipeline integration) — see proposal's Non-goals. `traceId` here is a minimal, per-response identifier, not a correlation mechanism wired into logging.
- No adoption of `api-naming-conventions` or `api-pagination` from the same reference store — separate proposals if adopted later.
- No versioning strategy for the breaking response-shape change (`openapi.yaml`'s `info.version` stays at `0.0.1`) — this repo has no established API-versioning convention yet; that gap is pre-existing and out of scope here.
- No change to `GET /health` — it has no error paths.

## Decisions

- **Central exception mapping via `@RestControllerAdvice`, not per-endpoint try/catch.** A single `@RestControllerAdvice` class maps every exception type this API currently throws into the envelope, so future endpoints inherit correct error behavior automatically instead of needing to remember to format errors themselves. No existing pattern to reuse or deviate from — this is the first cross-cutting concern in the repo.
- **Four exception types need mapping — confirmed empirically against a running instance, not assumed:**
  - `ResponseStatusException` — hand-thrown 404s (`getAsset`/`deleteAsset`).
  - `jakarta.validation.ConstraintViolationException` — thrown for the generated `AssetsApi`'s `@Min`-annotated `page`/`size` query parameters (confirmed via trace logging: `jakarta.validation.ConstraintViolationException: listAssets.page: must be greater than or equal to 0`). **Not** `HandlerMethodValidationException` as originally hypothesized before verification.
  - `org.springframework.web.bind.MethodArgumentNotValidException` — thrown by Bean Validation (`@Valid`) only when a field is *present but fails a constraint* (confirmed via `{"name":"","type":"image","status":"draft"}` → `MethodArgumentNotValidException` citing the `Size` violation on `name`).
  - `org.springframework.http.converter.HttpMessageNotReadableException` — thrown when a required field is *entirely absent from the JSON body*, because `CreateAssetRequest`'s Kotlin constructor parameters are non-nullable with no default: Jackson fails to construct the object during deserialization, before `@Valid`/Bean Validation ever runs (confirmed via `{"type":"image","status":"draft"}` → `HttpMessageNotReadableException: ... missing (therefore NULL) value for creator parameter name`). **This is the exception the existing `rejects request missing required field` test actually exercises** (it omits the key rather than sending an empty string) — design and test updates must account for both this and `MethodArgumentNotValidException` as two distinct "missing/invalid required field" paths, not one.
- **A pre-existing generated `@ControllerAdvice` already claims `ConstraintViolationException` and must be out-prioritized, not assumed absent.** `build/generated/openapi/.../generated/api/Exceptions.kt` (regenerated by `openApiGenerate`, gitignored, never hand-edited per this repo's convention) declares `DefaultExceptionHandler`, a `@ControllerAdvice` bean with `@ExceptionHandler(ConstraintViolationException::class)` that currently does `response.sendError(400, joinedMessages)` — which is why the page/size 400 has *some* message-passing today, just one `server.error.include-message`'s default (`never`) still swallows before it reaches the client. It carries no `@Order`, so it resolves at Spring's default (lowest) precedence. The new custom advice must declare a higher-precedence `@Order` (e.g. `@Order(Ordered.HIGHEST_PRECEDENCE)`) so its own `ConstraintViolationException` mapping is selected instead of the generated one — confirmed by re-running the generator and re-reading `Exceptions.kt` after Task 1.1, not assumed to disappear. The same generated class's `ApiException`/`NotFoundException`/`NotImplementedError` handlers are unused by this codebase (nothing throws them) and are left alone.
- **The blank-tags check becomes a thrown, structured validation failure instead of a raw `ResponseStatusException`.** Per the platform spec, a validation failure (400) must carry `error.details` with `field`/`code`/`message`. A bare `ResponseStatusException` reason string can't carry that structure. A small hand-written exception (`RequestValidationException(errors: List<FieldValidationError>)`, both plain Kotlin classes, no new dependency) is thrown by the controller for this one hand-written check and mapped by the same advice. This is the one hand-written exception type in the change — everything else maps from framework-thrown exceptions.
- **`HttpMessageNotReadableException`'s field name is extracted from its cause chain, not from a `BindingResult`.** Unlike `MethodArgumentNotValidException`, this exception has no field-error list — Jackson's underlying cause (`com.fasterxml.jackson.databind.exc.MismatchedInputException`/`InvalidNullException` in the `tools.jackson.databind` package used by this project's Jackson 3 setup) exposes a `path` describing which property failed to bind. The handler walks that path to build a single `error.details` entry; if the cause shape is ever something other than a missing-property binding failure (malformed JSON, wrong type), the handler falls back to a generic `error.details` entry naming no specific field rather than throwing internally.
- **`error.code` values, one per condition, assigned now rather than left generic:** `ASSET_NOT_FOUND` (404 on get/delete), `VALIDATION_FAILED` (400 on any request-validation failure — missing required field, invalid page/size, blank tags), with `error.details[].code` distinguishing the specific field-level reason (`REQUIRED`, `INVALID_VALUE`, `BLANK_VALUE`). One shared top-level `VALIDATION_FAILED` code (rather than a distinct top-level code per field) matches the platform spec's own shape — `error.code` identifies the *class* of error, `error.details` carries the per-field specifics — and keeps the set of top-level codes small and stable as more validated fields are added later.
- **`traceId`: a `UUID.randomUUID().toString()` generated inside the advice per error response.** No existing request-scoped identifier exists to reuse (confirmed: no filter, no MDC, no MicroMeter Tracing dependency in this repo). A per-response UUID meets the spec's literal requirement (a `traceId` string field is present) without introducing tracing infrastructure, which is explicitly out of scope (see Non-Goals). Alternative considered: a servlet filter assigning one `traceId` per request (reusable across logs) — rejected for now as speculative infrastructure with no consumer (no centralized logging to correlate against yet); revisit if/when logging/observability is added.
- **`Error`/`ErrorDetail` as generated OAS models, not hand-declared DTOs.** Per this repo's established rule, request/response shapes for OAS-covered endpoints come from generated models. `Error` and `ErrorDetail` are added to `openapi/openapi.yaml`'s `components/schemas` and referenced from every documented 4xx/404 response across `AssetController`'s operations; the `@RestControllerAdvice` constructs instances of the generated `Error`/`ErrorDetail` classes, matching how `AssetController` itself already only ever constructs generated response models.
- **All existing `asset-management` error scenarios are retrofitted in this same change, not phased.** The proposal already scopes this as a `Modified Capability` covering every current error condition. Splitting it (e.g., fixing only the tags case now, deferring 404/pagination errors) would leave the API with two error-body shapes simultaneously mid-migration, which is the exact inconsistency this change exists to remove.

## Risks / Trade-offs

- [Breaking change to already-shipped 400/404 response bodies] → No known external consumers (personal sandbox project per `docs/tech-stack.md`); accepted as a low-risk, single-step change rather than a phased/versioned rollout.
- [Assuming the wrong exception type for method-parameter or missing-field validation would leave that path unmapped, falling through to the framework default body] → Resolved during planning by triggering each path against a running instance and reading the actual exception class from trace logs (see Decisions) rather than left as an implementation-time discovery; still backed by an integration test per error path so a future regression fails the suite rather than passing silently.
- [The new custom advice and the generated `DefaultExceptionHandler` both target `ConstraintViolationException`; without an explicit `@Order` the two could resolve non-deterministically or the generated one could win] → Mitigated by giving the custom advice explicit `@Order(Ordered.HIGHEST_PRECEDENCE)` and verifying post-implementation (Task 3.2's own path) that the envelope, not the generated handler's raw `sendError`, is what actually responds.
- [A per-response random `traceId` cannot be used to correlate multiple log lines from the same request, unlike a request-scoped identifier] → Accepted per Non-Goals; revisit only if/when this repo adds structured logging or tracing.
- [Existing tests asserting only `status()` would not catch a regression in the error body shape] → New/updated tests assert the envelope fields (`error.code`, `error.message`, `error.traceId` presence, `error.details` for validation cases) for every retrofitted error path, not just status codes.

## Migration Plan

Single-step change, no feature flag or phased rollout (no external consumers to break gradually). Order: (1) add `Error`/`ErrorDetail` to `openapi/openapi.yaml` and regenerate, (2) implement the `@RestControllerAdvice` (ordered ahead of the generated `DefaultExceptionHandler`) mapping the four confirmed exception types, plus the one hand-written `RequestValidationException` for the tags check, (3) update `AssetController` call sites to throw the new structured exception where needed (tags) and let the advice handle the rest, (4) update/add tests per error path — including both the missing-key and empty-string-present variants of the "required field" scenario, since they now exercise different exception types, (5) update `docs/tech-stack.md`'s error-response line. Rollback is a plain revert (no data migration, no persisted state involved).

## Open Questions

- None blocking implementation. `error.code` is left as a free-form string in the OAS schema (matching the platform spec's own wording, "a SCREAMING_SNAKE_CASE string") rather than a closed OAS `enum`, so adding a new error condition later doesn't require a schema-breaking enum change.
- The four exception types to map, and the `@Order` requirement against the generated advice, were confirmed empirically during planning (see Decisions) rather than left as an implementation-time unknown.
